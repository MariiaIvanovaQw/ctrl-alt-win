# Введение

Документ описывает платформу подбора ИТ-специалистов с верифицированным
профилем ФСП. Разделы 1-8 соответствуют перечню раздела 3.4 технического
задания, раздел 9 – требованиям безопасности из раздела 3.5, приложение –
сверка с требованиями ТЗ.

**Суть решения.** Кандидат проходит опрос и персональный тест и получает
подтверждённую категорию: IT-направление и грейд, например «Бэкенд ·
Middle». Работодатель описывает потребность, получает подборку с
обоснованием каждого места и сам приглашает выбранного кандидата, указав
вилку зарплаты. Контакты кандидата открываются только после того, как он
принял приглашение или сам откликнулся на вакансию.

**Состав:** веб-приложение (кабинеты кандидата, работодателя и
модератора), API с бизнес-логикой, реляционная база данных, банк из 720
заданий с алгоритмами сборки теста и определения грейда, имитация ФСП ID
и реестра достижений в формате Keycloak.

# 1. Функциональная и компонентная архитектура

## 1.1. Роли

| Роль | Функции |
|---|---|
| Кандидат | регистрация по почте или вход через ФСП ID; анкета вручную или из PDF-резюме; опрос и тест; категория и история грейда; приглашения, переписка, отклики на вакансии; регулярные задания; приватность, согласия, выгрузка и удаление данных |
| Работодатель | профиль компании; потребности и вакансии; подборка с обоснованием; поиск по банку кандидатов; приглашения и отклики; регулярные задания; вебхуки для ATS |
| Модератор | рассмотрение компаний, приостановленных после жалоб; метка «Компания проверена» |
| Законный представитель | согласие на участие кандидата 15-17 лет по ссылке из письма |

Основной сценарий: регистрация → опрос (направление, специализация,
заявленный грейд) → тест из 26 заданий → категория → по желанию привязка
ФСП ID → работодатель описывает потребность и получает подборку →
приглашение с вилкой → кандидат принимает → работодатель видит контакты.
Дополнительно: вакансии и отклики, переписка до раскрытия контактов,
регулярные задания, жалобы на недобросовестные предложения.

## 1.2. Компоненты

```
 Веб-приложение ──HTTPS, JSON──► API (FastAPI) ──► PostgreSQL / SQLite
 (React)                          │  маршруты → сервисы → модели
                                  ├──► банк заданий (библиотека Python)
                                  ├──► почта (SMTP)
                                  ├──► ФСП ID и реестр (OpenID Connect)
                                  └──► ATS работодателя (вебхуки)
```

| Компонент | Назначение | Технологии |
|---|---|---|
| Веб-приложение | кабинеты всех ролей, публичные страницы | React, TypeScript, Vite |
| API | бизнес-логика, права, спецификация OpenAPI | Python, FastAPI, SQLAlchemy |
| База данных | профили, попытки, подборки, приглашения, журналы | PostgreSQL в контейнере, SQLite локально |
| Банк заданий | задания, сборка теста, подсчёт, определение грейда | собственная библиотека без зависимостей |
| Провайдер входа | токены в формате Keycloak; при необходимости – внешний Keycloak | PyJWT |
| Имитация ФСП ID | адреса и протоколы Keycloak, реестр достижений | встроенный модуль |
| Фоновые задачи | отправка вебхуков, очистка устаревших данных | потоки внутри API |

API – модульный монолит с явными слоями: маршруты проверяют данные и
права, сервисы содержат логику, модели описывают хранение. Модули
(идентичность, кандидаты, тестирование, подбор, взаимодействие, ФСП,
задания, интеграции) общаются только через сервисный слой, поэтому любой
из них можно вынести в отдельный сервис. API не хранит состояние в
памяти процесса и масштабируется числом процессов: ключ подписи токенов
общий, каждое событие для ATS отправляет ровно один процесс.

Схема базы создаётся при первом запуске; новые колонки и индексы
добавляются в существующую базу автоматически.

# 2. Механика тестирования

## 2.1. Порядок прохождения

1. **Опрос.** Направление (бэкенд, фронтенд, тестирование), специализация
   внутри него (Python, React, автоматизация и т. д.) и заявленный грейд.
   Без опроса тест недоступен.
2. **Выбор уровня.** Для каждого уровня видно, доступен ли тест, а если
   нет – почему и с какой даты.
3. **Тест.** 26 заданий, 60 минут. Ответы сохраняются по одному, попытка
   переживает перезагрузку страницы и завершается по истечении времени.
4. **Результат.** Балл, подтверждённый уровень, разбор по полосам
   сложности и компетенциям, каждое условие грейда с отметкой о
   выполнении. Правильные ответы не показываются.

## 2.2. Банк заданий

| Показатель | Значение |
|---|---|
| Заданий | 720: по 240 на направление, по 80 на уровень, по 240 каждого типа |
| Типы | теория, ситуационные кейсы, практические задания с кодом и данными |
| Конкретных форм | 856: у 76 заданий 2-4 варианта с другими числами и кодом |
| Компетенций | 16 / 16 / 15 на направление |
| Проверка | автоматическая для всех заданий: вариант, число или точная строка |
| Сложность | шкала 1-10, вес задания 1-4 балла |

В тесте 8 теоретических, 10 ситуационных и 8 практических заданий:
ситуационные лучше всего отделяют практический опыт от знания теории.

**Как подготовлен банк.** Задания подготовлены заранее с помощью
языковых моделей: ChatGPT Go (OpenAI) составлял промпты, Claude Opus 5.5
(Anthropic) по ним писал задания – условия, код, варианты, эталонные
ответы, объяснения, разметку компетенций и сложности. Персональные
данные в модели не передавались. Каждое задание прошло 13 статических
проверок (единственность правильного ответа, дубликаты, равномерность
букв ответа, отсутствие подсказки длиной варианта и др.) и 6 проверок на
синтетических кандидатах. Платформа в работе к языковым моделям не
обращается: сборка, проверка и грейд детерминированы.

## 2.3. Сборка персонального теста

* **Сид попытки** – криптографически случайное 64-битное число. Из него
  выводятся набор заданий, выбранные варианты, порядок заданий и порядок
  ответов. Сид не передаётся в браузер.
* **Единый план уровня**: одинаковое число заданий каждого типа и полосы
  сложности, обязательные компетенции покрыты, не больше 4 заданий на
  компетенцию, не меньше 8 компетенций. Сумма баллов у всех вариантов
  уровня одинакова, поэтому результаты сопоставимы.
* **Разные задания у разных кандидатов**: пересечение двух вариантов
  одного уровня – в среднем 32 %. Из пяти сидов выбирается тот, где
  меньше заданий, уже показанных кандидату, затем – реже показанных
  другим.
* **Браузер получает только** текст задания, код и варианты. Идентификатор,
  компетенция, сложность, вес и ключи остаются на сервере; ответ
  отправляется по номеру позиции.

Тест един для категории, а не для вакансии, иначе кандидатов нельзя было
бы сравнивать. Требования вакансии учитываются в подборе (раздел 3.3) и в
регулярных заданиях работодателя.

## 2.4. Грейд и правила пересдачи

Грейд определяется правилами банка и зависит от заявленного уровня теста.
Учитывается профиль результата, а не только общий балл: например, Senior
требует не менее 70 % баллов на заданиях сложности 7-10, не менее 12
решённых таких заданий и не менее 50 % на заданиях 9-10. Результат
должен превышать уровень случайного угадывания.

| Ситуация | Решение |
|---|---|
| Заявленный уровень подтверждён | присваивается категория |
| Результат выше заявленного | присваивается заявленный уровень и на 30 дней открывается тест следующего без ожидания; повышение – только отдельным тестом |
| Результат ниже заявленного | кандидат сам решает: принять рекомендованный уровень или пройти тест этого уровня; принудительного понижения нет |
| Неудачная попытка повышения | действующий грейд сохраняется |
| Тест не пройден | кандидат виден со статусом «грейд не подтверждён» ниже подтверждённых |

Ограничения: смена грейда – не чаще раза в 90 дней; повтор того же
уровня – через 30 дней; после неудачи сразу открыты только уровни ниже;
рекомендация уровня ниже выдаётся, только если за 180 дней не было
неудач; одна активная попытка, брошенная засчитывается. Кандидат может
подтвердить категории в нескольких направлениях – грейд хранится
отдельно для каждого.

## 2.5. Устойчивость к распространению заданий

| Мера | Действие |
|---|---|
| Объём банка | одна попытка видит около 11 % заданий направления |
| Персональный вариант | свой набор заданий, форм и порядок ответов |
| Перестановка ответов | буква правильного ответа случайна, по банку распределение A/B/C/D ≈ 25 % |
| Нет подсказок формой | правильный вариант самый длинный в 26 % форм при случайных 25 %; стратегии «самый длинный» и «по словам вопроса» дают уровень угадывания |
| Закрытые ответы | ключи и объяснения не покидают сервер ни во время, ни после попытки |
| Время и пересдачи | 60 минут на 26 заданий; правила раздела 2.4 не дают набрать категорию угадыванием |
| Признаки для разбора | быстрые верные ответы на сложные задания, уход со вкладки, копирование и вставка; видны работодателю, на грейд не влияют |
| Антиплагиат | совпадение неверных ответов с чужой попыткой сверх случайного (вероятность не выше 1 на 1000) и дословно похожие ответы «предложите подход» |

Передать можно только знание, а не ответ: чтобы ответить верно, нужно
понять, какая форма задания досталась и какой из показанных вариантов
правилен. Это и измеряет тест. На 309 независимых синтетических попытках
ложных признаков антиплагиата нет.

# 3. Механика подбора и категоризация

## 3.1. Категория

**Категория – IT-направление и подтверждённый тестом грейд.** Резюме,
самооценка и заявленный стек на неё не влияют. Специализация внутри
направления показывается в карточке и фильтрах, но категорию не дробит.
Кандидаты без подтверждения видны со статусом («тест ещё не пройден»,
«не подтвердил уровень», «решает, принять ли рекомендацию») и всегда
стоят ниже подтверждённых; работодатель может скрыть их фильтром.

Порядок внутри категории задаёт сила профиля:

```
сила = 0,60 × результат теста + 0,25 × достижения ФСП + 0,15 × актуальность
```

Результат теста сравним между кандидатами, проходившими разные уровни:
берётся доля баллов на полосах сложности категории, сглаженная к
среднему по категории, и место среди кандидатов категории.

## 3.2. Профиль потребности

Работодатель указывает название, направление, грейд, описание задач и
команды, стек, формат работы, город и обязательную вилку зарплаты. По
описанию строится профиль компетенций: вес компетенции зависит от её роли
для уровня, указанного стека и упоминаний в тексте. Навыки распознаются по
словарю из 67 навыков и 168 синонимов на русском и английском.
Работодатель видит восемь главных компетенций и источник веса каждой.

## 3.3. Подборка

В подборку входят кандидаты с согласием на показ профиля, открытые к
предложениям, из трёх категорий: основной, «с запасом квалификации»
(уровнем выше) и «на вырост» (уровнем ниже).

```
балл = (0,35 × компетенции + 0,25 × тест + 0,15 × стек
        + 0,15 × ФСП + 0,10 × актуальность) × (1 − штраф за условия)
```

| Фактор | Содержание |
|---|---|
| Компетенции | оценки компетенций по тесту, взвешенные по профилю потребности; оценки сглажены, поэтому одно задание не даёт 0 или 100 % |
| Тест | результат на заданиях уровня категории и место в категории |
| Стек | доля требуемых навыков; навык без подтверждения тестом связанной компетенции считается наполовину |
| ФСП | вес подтверждённых достижений (раздел 5.3) |
| Актуальность | давность активности и качество решения регулярных заданий |

Штраф за условия: ожидания выше вилки – 0,15, другой формат работы –
0,10, другой город без готовности к переезду – 0,10, всего не более 0,4.
Если ожидания не указаны или город скрыт, штрафа нет, но работодатель
видит предупреждение. Скрытые кандидатом сведения не участвуют ни в
ранжировании, ни в фильтрах, ни в объяснении.

Подборка сохраняется с параметрами; уточнение фильтров создаёт новую
подборку со ссылкой на прежнюю, поэтому прежний результат не теряется.

## 3.4. Объяснение выдачи

Для каждого кандидата: вклад каждого фактора с текстом, сильные стороны
(«SQL 96 %»), предупреждения («Ожидания выше вилки», «Нет в заявленном
стеке: Kafka»), роль категории. Обоснование сохраняется в приглашении –
кандидат видит, почему его пригласили.

## 3.5. Поиск и выход на контакт

* **Поиск по банку кандидатов** – по направлению, специализации, грейду,
  навыкам, наличию достижений ФСП, городу, формату, ожиданиям и тексту;
  только по сведениям, которые кандидат разрешил показывать.
* **Приглашение** – описание, обязательная вилка (рублей в месяц до НДФЛ),
  компания и способ связи; вакансия не обязательна. Статусы: отправлено,
  просмотрено, принято, отклонено (с причиной), отозвано, истекло
  (14 дней). Обе стороны видят статус и хронологию.
* **Контакты** открываются только компании, чьё приглашение принято или
  на чью вакансию кандидат откликнулся; каждый просмотр пишется в журнал
  аудита. Кандидат может закрыть доступ.
* **Переписка** в приглашении и отклике – до раскрытия контактов.
* **Вакансии и отклики** – классический сценарий: публикация с вилкой,
  отклик, ответ работодателя.
* **Регулярные задания.** Работодатель создаёт короткие задачи; платформа
  раз в 14 дней предлагает их кандидатам подходящей категории, работодатель
  может предложить задание адресно. Выбор и число проверяются
  автоматически, «предложите подход» оценивает работодатель.

## 3.6. Недобросовестные работодатели и ATS

Реализовано: показатели компании и предупреждения о неправдоподобной
вилке в приглашении; жалобы кандидатов; приостановка компании, если за
30 дней пожаловались не менее трёх разных кандидатов, взаимодействовавших
с ней, и это не меньше 20 % ответов; решение модератора; добровольная
проверка компании по ИНН с меткой «Компания проверена»; лимит приглашений
в сутки. Для ATS – вебхуки о приглашениях, откликах и заданиях с подписью
HMAC-SHA256 и повторами при недоступности, выгрузка кандидата в JSON Resume.

Концепция развития: сверка ИНН с ЕГРЮЛ и доменом сайта, скоринг
вакансий по рыночной вилке и тексту, двусторонняя синхронизация вакансий и
статусов через API с OAuth-клиентом компании.

# 4. Процедура валидации и результаты

## 4.1. Методика

Данные синтетические. Генератор задаёт каждому кандидату скрытый
«истинный» профиль: уровень, силу по каждой компетенции, настоящий стек и
ожидания. Платформа его не видит: кандидаты проходят тест по общим
правилам, затем результаты сравниваются с истиной.

* 5 независимых наборов по 240 кандидатов;
* 15 потребностей: 6 демо-вакансий и 9 типовых профилей ролей;
* сравнение: тест против самооценки, подбор против поиска по резюме и
  случайного порядка;
* всё воспроизводится одной командой (`python -m scripts.evaluate`),
  отчёт – `backend/reports/evaluation_report.md`.

## 4.2. Результаты

**Категоризация**

| Явно завышенный уровень | **0 %** | 10,3 % |
| Явно заниженный уровень | 4,0 % | 3,3 % |
| Кандидатов с подтверждённой категорией | 83,5 % | 100 % |

**Подбор** (тестовый набор пар «вакансия – кандидат»)

| Метод | P@10 | nDCG@10 |
|---|---|---|
| **Подбор платформы** | **0,78** | **0,94** |
| Платформа без учёта ФСП | 0,74 | 0,93 |
| Поиск по резюме (заявленный стек, уровень, опыт) | 0,56 | 0,83 |
| Просмотр категории без ранжирования | 0,47 | 0,76 |
| Случайный порядок | 0,19 | 0,60 |

В первой десятке подборки нет кандидатов явно ниже уровня (у поиска по

все навыки направления, попадают в первую десятку в доле, близкой к их
доле в пуле (24 % при 20 %).

**Стабильность при повторном прохождении** (другой сид – другие задания):
тот же уровень у типичных кандидатов в 75-98 % повторов, у пограничных
профилей – 53-68 %. Колебания не дают скачков категории: грейд не

**Различающая сила заданий** (310 попыток демо-данных): медиана
точечно-бисериальной корреляции 0,39, у 78 % заданий не ниже 0,2;
заявленная сложность согласуется с долей верных ответов (−0,75). Слабые
задания отмечаются для пересмотра: `python -m scripts.item_analysis`.

**Угадывание с пересдачами в течение года**: без ограничений категорию

**Производительность**: 50 одновременных пользователей, 240 кандидатов в

# 5. Интеграция с реестром ФСП

## 5.1. Схема

API и структура данных ФСП не предоставлялись; известно, что ФСП ID
будет работать на Keycloak. Поэтому интеграция построена на стандартных
протоколах Keycloak: OpenID Connect для входа пользователя и сервисная
авторизация для запросов к реестру.

1. Кандидат даёт согласие на получение сведений из реестра и нажимает
   «Привязать ФСП ID».
2. Браузер уходит на страницу входа ФСП ID; запрос защищён параметром
   `state` и PKCE.
3. ФСП ID возвращает кандидата; привязку завершает тот же пользователь,
   который её начал.
4. Платформа проверяет подпись токена, получает постоянный идентификатор
   участника и запрашивает в реестре его данные и достижения.
5. Снимок достижений хранится в профиле, обновляется по кнопке и
   удаляется при отвязке.

Поддерживается и вход через ФСП ID: при первом входе профиль кандидата
создаётся автоматически.

## 5.2. Сведения и их учёт

| Сведения | Назначение |
|---|---|
| Мероприятие, дата, ссылка на подтверждение | проверяемый факт участия |
| Дисциплина и уровень мероприятия | контекст, на вес не влияют |
| Итог и место | основа веса |
| Роль и команда | показываются, бонуса не дают |
| Отметка о подтверждении реестром | в расчёт идут только подтверждённые |
| Спортивный разряд | показывается в карточке |

```
вес достижения = вес итога × e^(−лет с даты / 3)
ФСП = 1 − e^(−(сумма весов результатов + min(0,3; сумма весов участий)) / 1,2)
```

Веса итога: победитель 1,0, призёр 0,75, финалист 0,4, участник 0,1.
Дисциплины и соревнования равноценны, свежие результаты весят больше.
Достижения ФСП влияют только на место внутри категории, не на грейд.

**Кандидат без истории ФСП** получает по этому фактору 0 без штрафа:
остальные факторы считаются как обычно, а в карточке нейтральный текст –
отсутствие истории ФСП не влияет на категорию и грейд.

## 5.3. Подключение настоящего ФСП ID

Имитация реализует те же адреса и протоколы, что Keycloak, поэтому
переход – смена настроек (`APP_FSP_MODE=oidc`, адрес realm, адрес реестра,
клиент и секрет), без изменения кода. От ФСП нужны: клиент с адресом
возврата и сервисной учётной записью; в токене – постоянный идентификатор
участника и подтверждённая почта; метод реестра «достижения участника по
идентификатору».

# 6. Описание API

* Все методы описаны спецификацией OpenAPI: на сервере – `/docs`
  (Swagger UI) и `/redoc`, в репозитории – `docs/openapi.json`. Для
  каждого метода указаны схемы запроса и ответа и коды ошибок: 111 адресов,
  133 операции.
* Базовый путь `/api/v1`, JSON в UTF-8, время в UTC, суммы – рубли в месяц
  до вычета НДФЛ. Кандидат во внешних ответах обозначается псевдонимом
  вида `C-7KQ2M9X`, внутренние идентификаторы наружу не передаются.
* Токен передаётся в заголовке `Authorization: Bearer`. Токены в формате
  Keycloak (`realm_access.roles`, подпись RS256, ключ публикуется как
  JWKS): доступ – 30 минут, обновление – 14 дней с ротацией; повторное
  предъявление использованного токена завершает все сессии. Режим
  `APP_AUTH_MODE=keycloak` принимает токены внешнего Keycloak.
* Разделы `/candidate/*`, `/employer/*`, `/admin/*` доступны только своей
  роли; принадлежность записи проверяется в каждом запросе.

Ошибки – в едином формате:

```json
{"error": {"code": "grade_change_cooldown", "message": "Грейд можно менять не чаще раза в 90 дней",
           "details": {"available_at": "2026-12-01T10:00:00+00:00"}}}
```

Коды HTTP: 400 – нарушено правило, 401 – нет токена, 403 – нет прав, 404 –
не найдено или чужое, 409 – конфликт состояния, 413 – большой запрос,
422 – ошибка полей, 429 – превышена частота.

# 8. Сборка, развёртывание и локальный запуск

Нужны Python 3.10+ и Node.js 20+ либо Docker с Compose. Внешние сервисы
для локального запуска не нужны: SQLite, встроенный провайдер входа и
имитация ФСП ID.

**В контейнерах** (из корня репозитория):

```bash
docker compose up --build
```

Поднимаются веб-приложение (http://localhost:5173), API
(http://localhost:8000/docs, 4 процесса), PostgreSQL и Mailpit
(http://localhost:8025). При первом запуске база заполняется демо-данными
(около минуты). Пароли и адреса переопределяются в файле `.env` рядом с
`docker-compose.yml`. Профиль `keycloak` добавляет Keycloak с realm
`platform`.

**Без Docker.** API (из каталога `backend`):

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
python -m scripts.seed_demo --reset
uvicorn app.main:app --port 8000
```

В Linux и macOS – `source .venv/bin/activate` и `cp .env.example .env`.
Файл `.env` из примера включает демо-режим; без него API запускается в
безопасном режиме, без служебных методов и имитации ФСП ID.
Веб-приложение (из каталога `frontend`, во втором терминале):

```bash
npm install
npm run dev
```

**Демо-доступ.** `seed_demo` создаёт 240 кандидатов, 3 компании и
6 вакансий и записывает учётные записи в `backend/data/demo_accounts.json`
(в Docker – `docker compose exec api cat /data/demo_accounts.json`):
жюри `jury1…jury5@demo-fsp.ru` – чистые кандидаты для прохождения теста,
работодатели `hr1…hr3@demo-fsp.ru`, кандидаты с тестом и без, модератор.
На странице входа демо-учётные записи подставляются одним кликом. В
демо-режиме есть экспресс-режим теста (несколько заданий вручную,
остальные дозаполняются по выбранному профилю, 3-5 минут) и сброс
попыток. Все люди, компании и достижения в демо-данных вымышлены.

**Проверка.** `python -m pytest` в `backend` – 138 автотестов (тот же
набор проходит на PostgreSQL 16 через `TEST_DATABASE_URL`);
`ruff check .` в корне; `npm run lint` и `npm run build` во `frontend`;
`python tools/validate_bank.py` и `python tools/simulate_candidates.py` в
`it-assessment-bank`.

* Обработка данных – с согласия, согласия хранятся с версией и датой;

  работодатель видит фамилию и инициал; кандидат может скрыть город, «О

  стираются профиль, ответы, переписка и копии писем.

  пароля, размер тела запроса; защита от предзахвата учётной записи и
  SSRF в вебхуках.
* Регистрация только с почтой в домене `.ru` (данные граждан РФ
  обрабатываются в РФ).
* Кандидаты 14-17 лет: тест – с 14 лет; показ работодателям, приглашения
  и отклики – с 15 лет и с согласия законного представителя; приглашать
  можно только на предложения с лёгким трудом и сокращённым временем.
