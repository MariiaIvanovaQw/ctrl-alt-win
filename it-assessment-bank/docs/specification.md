# Спецификация банка заданий

Нормативный источник чисел – `tools/blueprint.py`; эталонная реализация
алгоритмов – `tools/`. Статистика банка формируется командой
`python tools/build_bank.py` в `dist/statistics.md`.

## 1. Модель компетенций

```
specialization → level → competency → item
backend          middle   sql          BE-M-T-011
```

Идентификатор `FE-J-T-001`: направление (FE, BE, QA), уровень (J, M, S),
тип (T – theory, S – situational, P – practical), номер в файле.
Идентификатор неизменяем: при переработке задания создаётся новый.

| Направление | Компетенции |
|---|---|
| frontend (16) | html, css, javascript, typescript, react, state_management, components, api_integration, http, browser, performance, security, accessibility, git, architecture, testing |
| backend (16) | programming_language, algorithms, data_structures, databases, sql, http, rest_api, auth, security, performance, caching, concurrency, architecture, scalability, git, testing |
| qa (15) | requirements_analysis, test_design, test_cases, checklists, bug_reports, functional_testing, regression_testing, integration_testing, api_testing, sql, test_automation, load_testing, risk_analysis, defect_prioritization, test_documentation |

Роли компетенций: `MANDATORY` – обязана быть в каждой попытке; `KEY` –
«нет провала по основным темам» при определении грейда; `CRITICAL` –
дополнительное требование для Senior.

```
frontend  mandatory: javascript, react, css, api_integration, state_management
          key:       mandatory + components, typescript
          critical:  security, performance, architecture
backend   mandatory: sql, databases, rest_api, security, performance
          key:       sql, databases, rest_api, programming_language, algorithms, http, data_structures
          critical:  security, architecture, scalability, performance, concurrency
qa        mandatory: test_design, test_cases, bug_reports, api_testing, sql
          key:       mandatory + requirements_analysis, functional_testing, checklists
          critical:  risk_analysis, test_automation, integration_testing, load_testing
```

На компетенцию – от 4 (ниже – ошибка) до 32 заданий, цель – от 8.

## 2. Сложность и баллы

Сложность 1-10 содержательная: задание получает её по наибольшему
требуемому признаку – вывод о системе целиком (9-10), выбор между
несколькими правильными решениями с ценой каждого (7-8), диагностика по
симптому или взаимодействие компонентов (5-6), применение известного
правила (4), знание инструмента или определения (1-3). Объём кода и
редкость факта сложность не повышают.

| difficulty | Уровень | Полоса | Вес (`score`) |
|---|---|---|---|
| 1-3 | junior | easy | 1 |
| 4-6 | middle | mid | 2 |
| 7-8 | senior | hard | 3 |
| 9-10 | senior | top | 4 |

Частичных баллов нет: задание даёт `score` или 0, пропуск равен неверному
ответу. Типы проверки: `single_choice` (679 заданий), `numeric` (30,
точность 1e-9, запятая и пробелы допускаются), `exact_match` (11, с
нормализацией `trim` / `lowercase` / `remove_spaces` /
`collapse_whitespace`); `multiple_choice` и `code_output` поддержаны схемой.

```
score            = round(100 · points_earned / points_possible)
competency_score = round(100 · earned_c / possible_c)      # confidence = low при possible_c < 4
band_rate        = earned_band / possible_band              # null, если заданий полосы не было
chance_baseline  = round(100 · Σ(score / число вариантов) / points_possible)
```

Компетенции с `confidence = low` показываются с пометкой и в грейде не
участвуют. `chance_baseline` для теста из 26 заданий ≈ 24 и сам
подстраивается под долю заданий со свободным вводом. Не используются:
отрицательные баллы, время ответа как часть балла, множители по
компетенциям – они делают балл непрозрачным.

## 3. Сборка персонального теста

Вход: направление, заявленный уровень, 64-битный сид. Выход: 26 заданий в
порядке показа с выбранными формами и перемешанными ответами, ключи
проверки – только для сервера.

| Тип | Junior (34 балла) | Middle (54 балла) | Senior (81 балл) |
|---|---|---|---|
| theory | 6 × d1-3, 2 × d4-5 | 2 × d2-3, 5 × d4-6, 1 × d7-8 | 2 × d4-6, 4 × d7-8, 2 × d9-10 |
| situational | 7 × d1-3, 2 × d4-5, 1 × d6 | 1 × d2-3, 6 × d4-6, 3 × d7-8 | 2 × d4-6, 5 × d7-8, 3 × d9-10 |
| practical | 5 × d1-3, 3 × d4-5 | 1 × d2-3, 5 × d4-6, 2 × d7-8 | 1 × d4-6, 4 × d7-8, 3 × d9-10 |

Ограничения: без повторов; не больше одного задания из `version_group`;
не больше 4 заданий на компетенцию; не меньше 8 компетенций; все
`MANDATORY` присутствуют.

1. **Пулы ячеек.** Задания ячейки (тип × диапазон сложности) сортируются
   по `id` и перемешиваются подпотоком `pool:<spec>:<level>:<type>:<dmin>-<dmax>`.
2. **Основной проход.** Для каждого места берётся допустимое задание с
   наименьшим рангом `(0, если компетенция ещё нужна, иначе 1; сколько
   заданий этой компетенции уже выбрано; позиция в пуле)`.
3. **Ремонт покрытия.** Если обязательная компетенция не покрыта, задание
   компетенции, представленной дважды, заменяется в своей ячейке.
   Невозможность замены – дефект банка, его ловит проверка V12.
4. **Порядок показа.** Перемешивание подпотоком `order:<spec>:<level>`,
   затем чередование типов situational → practical → theory.
5. **Рендеринг.** Выбор формы задания и перестановка ответов (раздел 4).

Клиент получает только `client_view`: позицию, тип, вопрос, код и
варианты; без `item_id`, формы, компетенции, сложности и веса. Метка
`test_id` – направление, уровень и 16 hex-цифр SHA-256 от сида; сид не
раскрывается. Повторная попытка получает новый сид; из пяти кандидатных
сидов берётся вариант с наименьшим пересечением с прошлыми попытками.
Пересечение двух случайных вариантов уровня – в среднем 32 %.

## 4. Сид и генератор

Генератор переносим между языками: реализация на любом языке по
описанию ниже даёт те же тесты.

```
splitmix64_next(state):            # беззнаковая 64-битная арифметика
    state = (state + 0x9E3779B97F4A7C15) & MASK64
    z = state
    z = ((z ^ (z >> 30)) * 0xBF58476D1CE4E5B9) & MASK64
    z = ((z ^ (z >> 27)) * 0x94D049BB133111EB) & MASK64
    return state, (z ^ (z >> 31)) & MASK64

fnv1a64(text): h = 0xCBF29CE484222325; для байта b UTF-8: h = ((h ^ b) * 0x100000001B3) & MASK64
sub_rng(seed, domain) = Rng((seed ^ fnv1a64(domain)) & MASK64)
below(n): limit = 2^64 − (2^64 mod n); повторять x = next() пока x ≥ limit; вернуть x mod n
shuffled(items): для i от len−1 до 1: j = below(i + 1); обменять items[i], items[j]
```

Домены подпотоков: `pool:…` (набор заданий ячейки), `order:<spec>:<level>`
(порядок), `variant:<item_id>` (форма задания), `options:<item_id>:<variant_id>`
(порядок ответов). Ключ проверки хранит показанные буквы, поэтому
«правильный ответ – B» бесполезен другому кандидату.

Контрольные значения:

```
Rng(0)       → 16294208416658607535, 7960286522194355700, 487617019471545679, 17909611376780542444
Rng(184729)  → 3423912569124784227, 5779354242648365914, 5435903768106855938, 12050495762681705875
fnv1a64("order") = 7774916592154454519
fnv1a64("options:FE-J-T-001:v1") = 15434515971773433591
Rng(184729).below(4) × 8 → 3, 2, 2, 3, 0, 2, 0, 1
sub_rng(184729, "order").shuffled(["A","B","C","D"]) = ["C","D","A","B"]
sub_rng(1, "pool").shuffled([0,1,2,3,4,5])           = [5,1,0,4,3,2]
```

Параметры, которыми управляет сид (`seed_parameters`): порядок ответов
(679 заданий), входные значения (407), имена переменных (158), длина
данных (1). Значения не подставляются на лету – сид выбирает одну из
заранее написанных форм (`variants`), поэтому эталон всегда известен.
Для восстановления попытки хранятся `seed` и `bank_version` либо список
`item_id` + `variant_id`.

## 5. Определение грейда

Реализация – `tools/grading.py`, пороги – `GRADE_RULES`. Наборы условий
проверяются в порядке senior → middle → junior, берётся первый
выполненный (иначе `below_junior`). Повышение – не больше одного шага
над заявленным уровнем; Senior подтверждается только тестом Senior.
Если заданий полосы в попытке не было, условие по ней считается
выполненным.

| Условие | Junior-тест → M / J | Middle-тест → M / J | Senior-тест → S / M / J |
|---|---|---|---|
| `overall_min` | 82 / 55 | 62 / 28 | 75 / 30 / 35 |
| `chance_margin_min` | 45 / 22 | 32 / 6 | 45 / 10 / 8 |
| `easy_rate_min` | – / 0,65 | – / 0,70 | – |
| `mid_rate_min` | – | – / 0,33 | – / 0,60 / 0,55 |
| `mid_plus_rate_min` (d4-10) | 0,70 / – | 0,58 / – | – |
| `mid_plus_solved_min` | 5 / – | 10 / – | – |
| `hard_rate_min` (d7-10) | – | – | 0,70 / 0,30 / 0,20 |
| `hard_solved_min` | – | – | 12 / – / – |
| `top_rate_min` (d9-10) | – | – | 0,50 / – / – |
| `key_floor` / допустимо ниже | 45 / 1, 25 / 3 | 40 / 1, 20 / 3 | 50 / 2, 30 / 1, 20 / 2 |
| `critical_covered_min`, `critical_avg_min` | – | – | 2 и 60 / – / – |

Решение сохраняется целиком (`grade_decision`): уровень по правилам,
ограничение повышения, исход (`confirmed` / `promoted` / `downgraded`),
метрики и каждая проверка с фактическим значением. `grade_confidence = low`,
если измерено меньше трёх ключевых компетенций. Достижимость шести
требуемых исходов на синтетике: J→J 79 %, J→M 88 %, M→M 79 %, M→J 54 %,
S→S 75 %, S→M 46 %; остаток уходит на соседний нижний исход.

Как исход меняет категорию, решает платформа: понижение – только
рекомендация, смена грейда раз в 90 дней, повтор уровня через 30 дней,
после неудачи уровень ниже подтверждается только тестом этого уровня
(180 дней), одна активная попытка, 60 минут.

## 6. Документ результата

Короткая форма – для карточки и фильтров: `specialization`,
`declared_level`, `confirmed_level`, `outcome`, `score`, баллы по
компетенциям, `test_id`. Полная форма дополнительно содержит
`points_earned` / `points_possible`, `competency_details` (баллы, число
заданий, `confidence`), `difficulty_buckets` по полосам, `grade_decision`,
`seed`, применённый план, состав теста (`item_id`, `variant_id`,
метаданные), ответы с отметкой верности и `finished_at`. Пример –
`dist/example_result.json`.

В результате нет правильных ответов, объяснений и ключей (ключи
восстанавливаются по сиду), а персональные данные заменены ссылкой на
кандидата. Ответы хранятся построчно – по ним считается статистика
заданий и пересматривается сложность.

## 7. Защита от передачи ответов

| Уровень | Мера |
|---|---|
| Объём | попытка видит около 11 % заданий направления |
| Персональный сид | разный набор, порядок, формы и разметка ответов |
| Перестановка ответов | буква правильного ответа случайна, распределение A/B/C/D ≈ 25 % |
| Формы задания | 76 заданий с 2-4 формами: ответ «3» верен для одной формы и неверен для другой |
| `version_group` | 501 группа: из группы в попытку попадает не больше одного задания |
| Свободный ввод | 41 задание требует числа или строки, «варианта B» у них нет |
| Защита от угадывания | условие `chance_margin_min`; случайные ответы почти всегда дают `below_junior` |
| Форма вариантов | правильный самый длинный в 26,3 % форм, самый короткий в 23,0 % |
| Скрытые поля | клиент не видит `item_id`, компетенцию, сложность и вес |

Передать можно только знание: для верного ответа нужно понять, какая
форма досталась и какой из показанных вариантов правилен. Признак утечки
задания – рост доли верных ответов при неизменных результатах по
остальным заданиям компетенции; такое задание выводится, его группа
пополняется. Генерация заданий и проверка ответов моделями в рантайме не
используются: это нарушило бы воспроизводимость и объяснимость.

## 9. Ограничения

1. **Разрешение теста из 26 заданий.** Исходы M→J и S→M достигаются в
   46-54 % прогонов, остальное смещается на шаг ниже. Повышает точность
   тест на 32-34 задания или вторая попытка при `grade_confidence = low`.
2. **Сложность задана экспертно.** Пересмотр – по статистике не менее
   100 попыток на задание: доля верных выше 0,90 у d7-10 – понизить, ниже
   0,25 у d1-3 – исправить задание.
3. **`multiple_choice` и `code_output`** поддержаны, но в банке не
   использованы: для MVP меньше типов интерфейса.
4. **Подсказка длиной варианта** была в версии 1.0.0 (правильный –
   самый длинный в 93 % форм) и устранена в 1.1.0; возврат ловят V13 и S6.
